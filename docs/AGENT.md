# 에이전트 구조 — 함정 모음

`Agent.kt` 가 띄우는 shell UID 프로세스에 관한 것. 여기 적힌 두 가지는 실기기에서
직접 밟은 뒤에야 알아낸 것들이고, 둘 다 증상이 원인을 가리키지 않는다.

## 왜 에이전트인가

`Settings.System.pass_through` 는 앱 UID 로 쓸 수 없다(AOSP 비공개 키 보호, `11-write-path.md`).
shell 이 필요하고, 앱이 shell 을 빌리는 유일한 길은 자기 기기의 adbd 에 ADB 클라이언트로
붙는 것이다.

값을 바꿀 때마다 그걸 하면 매번 무선 디버깅을 켜고, mDNS 로 포트를 찾고, TLS 로 붙어야 한다.
그 하나하나가 실패 지점이고, **무선 디버깅은 같은 수를 쓰는 다른 앱들과 다투는 자원이다**
(KeyMapper, lan-mouse-android, Shizuku …). 그중 하나가 자기 일을 끝내며 그걸 꺼버리면
포트가 바뀌고 우리 연결이 죽는다.

그래서 ADB 는 **부팅 후 한 번만** 쓴다. 에이전트를 띄우는 데에만. `pass_through` 는 어차피
재부팅마다 0 으로 초기화되므로 그 한 번은 피할 수 없는 비용이고, 에이전트는 그 위에 얹힌다.

부수 효과가 크다. 앱이 백그라운드에서 제때 깨어날 필요가 없어져서 **알람도, 포그라운드
서비스도, App Standby 와의 씨름도, 사용자에게 배터리 최적화를 꺼달라고 부탁하는 일도 없다.**
남은 알람은 20분마다 "에이전트 살아있나" 보는 감시견뿐이고, 그건 늦어도 상관없다.

## 함정 1 — `nohup` 만으로는 죽는다

증상: `execute()` 가 성공을 반환하는데 프로세스가 없다. 로그에는 "agent launched" 만 남는다.

원인: **ADB 세션이 닫히면 아직 그 프로세스 그룹 안에 있는 것이 함께 죽는다.** fork 는 됐지만
분리를 끝내지 못한 자식이 그 경주에서 진다. `adb shell` 로 같은 스크립트를 돌리면 매번
성공하는데 앱이 자기 ADB 로 돌리면 실패하는 이유가 이것이다 — 앱 쪽은 명령이 끝나는 즉시
연결을 닫기 때문이다.

대응 두 겹:

1. `setsid` 로 세션에서 떼어낸다. `nohup` 만으로는 기기에 따라 부족하다.
2. **기동 스크립트가 pid 파일이 채워진 것을 확인하기 전에는 반환하지 않는다.** 그래야
   반환 시점에 이미 분리가 끝나 있다. 경주 자체가 없어진다.

`lan-mouse-android` 의 `res/raw/start.sh` 에 같은 내용이 주석으로 적혀 있다. 우리는 그걸
보기 전에 같은 함정을 다시 밟았다.

## 함정 2 — shell 이 **만든** 파일을 앱은 읽지 못한다

증상: 에이전트는 멀쩡히 도는데 앱이 `EACCES` 로 죽는다.

앱과 에이전트는 앱의 external files 디렉터리로 통신한다 — 앱 UID 와 shell UID 가 함께 닿는
유일한 장소다. 그런데 접근이 대칭이 아니다.

| 방향 | 결과 |
|---|---|
| shell → 앱이 만든 파일에 쓰기 | **가능. 소유자가 앱으로 유지된다** |
| shell → 앱이 만든 파일 읽기 | 가능 |
| 앱 → **shell 이 만든** 파일 읽기 | **불가 (EACCES)** |

**누가 썼느냐가 아니라 누가 만들었느냐가 정한다.** 그래서 규칙은 하나다:

> 에이전트가 쓸 파일은 **앱이 먼저 빈 파일로 만들어 둔다.** 에이전트는 덮어쓰기만 하고
> (`> file`, `: > file`) 절대 지우지 않는다. 지우면 다음에 만들 때 shell 소유가 된다.

그래서 에이전트의 정지 경로도 `rm` 이 아니라 `: >` 로 비운다.

그리고 상태 파일 읽기는 전부 `runCatching` 으로 감싼다. 상태 표시 하나 때문에 앱이 죽어서는
안 된다 — 이 규칙을 어디선가 어기면 바로 그렇게 된다.

## 함정 3 — "살아있음" 판정이 표시와 복구를 동시에 오염시킨다

증상: 앱이 "running" 이라고 하는데 `last seen` 은 160초 전. 그리고 "Start agent" 를 눌러도
아무 일도 일어나지 않고, 로그에는 성공처럼 남는다.

원인: 심장박동 주기가 상황에 따라 다른데(충전 중 30초, 미연결 120초) 판정 임계값을
하나로 뒀다. 느린 쪽에 맞춰 200초로 잡으니, **충전 중에 죽은 에이전트를 3분 넘게
살아있다고 본다.**

나쁜 쪽은 화면이 아니다. `ensureRunning` 이 같은 판정을 쓰기 때문에 **"이미 돌고 있다" 며
되살리기를 건너뛴다.** 사용자가 할 수 있는 유일한 복구 동작이 조용히 무력화된다.

대응:

- 임계값을 주기별로 나눈다. `beat` 에 충전 여부가 이미 들어 있으니 그것으로 고른다
  (충전 중 90초 = 3주기, 미연결 300초 = 2.5주기).
- 앱을 열 때 에이전트가 죽어 있으면 스스로 되살린다. "앱은 멀쩡해 보이는데 아무것도
  안 돌고 있는" 상태를 남기지 않는다.

일반화하면 이렇다. **주기가 달라지는 심장박동은 판정 임계값도 같이 달라져야 한다.**
그리고 그 판정을 표시와 제어가 공유한다면, 관대한 쪽으로 틀리는 것이 더 위험하다.

## 함정 4 — 싼 판정이 정확한 판정으로 가는 길을 막는다

함정 3 을 고치면서 정확한 생존 확인을 만들었다. 앱이 토큰을 던지고 에이전트가 그것을
심장박동에 되돌려주면, "최근에 살아 있었다" 가 아니라 "지금 살아 있다" 가 된다.
(앱이 프로세스를 직접 볼 방법은 없다 — 안드로이드는 `/proc` 을 `hidepid` 로 마운트해서
`ps` 든 `/proc/<pid>` 든 자기 자신만 보인다.)

그런데 그 뒤로도 에이전트가 교체되지 않았다. 원인은 **호출하는 쪽마다 그 앞에 싼 판정을
하나씩 놓아둔 것**이었다.

```kotlin
if (!Agent.isAlive(context)) { ... ensureRunning() ... }   // ViewModel
if (!wasAlive) { ... ensureRunning() ... }                 // PolicyRunner
if (isAlive(context)) return ...                           // ensureRunning 자신
```

셋 다 "비싼 확인은 필요할 때만 하자" 는 같은 선의였다. 그런데 **싼 판정이 틀리는 방향이
하필 "죽었는데 살았다고 하는" 쪽**이라, 그 게이트가 정확한 확인으로 가는 길을 막는다.
한 번 틀리면 스스로 교정될 길이 없다.

교훈은 "게이트를 지워라" 가 아니다. **판정은 한 곳에서만 내린다.** `ensureRunning` 은
살아 있으면 즉시 돌아오므로 호출자가 앞질러 판단할 이유가 애초에 없었다. 싼 것과 비싼 것을
둘 다 공개해서 최적화할 여지를 만들어 준 API 설계가 원인이었다.

지금은 이렇다.

- `Agent.isAlive` — 심장박동 나이. **표시 전용.**
- `Agent.verifyAlive` — ping 왕복. **`ensureRunning` 안에서만 쓴다.**
- 되살릴지 말지는 `ensureRunning` 이 혼자 정한다.

## 함정 5 — 광고된 포트가 살아 있는 포트는 아니다

증상: "Start agent" 첫 시도가 `ECONNREFUSED` 로 실패하고, 다시 누르면 성공한다.
실패할 때 포트는 **매번 같다.**

원인: 무선 디버깅을 껐다 켜면 adbd 의 포트가 바뀌는데, 안드로이드 NSD 캐시에는 옛 레코드가
한동안 남는다. `AdbMdns.discoverPort` 는 처음 해석된 레코드를 그대로 돌려주므로, 죽은 쪽이
먼저 나오면 그걸 들고 가서 죽는다. `/proc/net/tcp` 로 확인해 보니 그 포트는 리스닝 목록에
아예 없었다.

대응: 해석된 포트를 **루프백으로 한 번 두드려 보고**, 응답하는 것만 채택한다. 거절은 즉시
돌아오므로 비용이 없다. 죽은 레코드는 건너뛰고 계속 찾는다.

이 앱은 무선 디버깅을 껐다 켜는 쪽이므로 스스로 이 상황을 만든다 — 다른 앱들도 같은 일을
한다. 캐시가 낡는 것은 예외가 아니라 정상이다.

## 파일

```
agent.sh     앱이 쓰고 shell 이 실행한다. 띄우기 직전에 항상 새로 쓴다
agent.conf   앱이 쓴다 — 모드 / low / high, 한 줄씩
agent.beat   에이전트가 덮어쓴다 — "epoch 잔량 충전여부 want pass_through"
agent.pid    에이전트가 덮어쓴다
agent.stop   앱이 만든다 — 에이전트가 보고 스스로 나간다
```

스크립트를 매번 새로 쓰기 때문에 **버전 동기화 문제가 없다.** lan-mouse 는 APK 안의 바이너리와
`/data/local/tmp` 의 사본을 sha256 으로 비교해야 했는데, 우리 에이전트는 셸 스크립트라
그냥 다시 쓰면 된다.

## 재부팅 복구 — 이 구조의 최종 시험

`pass_through` 는 재부팅마다 0 으로 초기화되고 에이전트도 함께 죽는다. 그래서 부팅 후
스스로 되살아나지 못하면 이 앱은 쓸모가 없다.

실측 (2026-08-30 11:27):

```
[boot_completed] agent launched · 80% plugged want=1 pass_through=1 (1s ago) · -3mA
```

일어난 일:

1. `BOOT_COMPLETED` → `PolicyReceiver` → `PolicyJobService`
2. `ensureRunning` 이 에이전트 부재를 확인 (ping 무응답)
3. 무선 디버깅을 켜고, **바뀐 포트를 mDNS 로 찾아** (42653 → 43073), ADB 로 붙어 에이전트 기동
4. 에이전트가 80% ≥ high(75) 를 판단해 `pass_through=1` 을 씀
5. 바이패스 발동 (−3 mA), 앱이 알림으로 보고

**사용자 개입 0회.** 앱을 열지도 않았다.

부수 확인:
- `adb_allowed_connection_time = 0` 이 다시 설정됐다 — 페어링이 만료되지 않는다
- 재부팅 후 새로 만들어진 파일이 전부 앱 소유였다 (함정 2 재발 없음)
- 데스크탑의 `adb` 는 같은 순간 포트 변경 때문에 붙지 못했다. 앱은 붙었다 —
  mDNS 탐색을 직접 구현해 둔 값어치가 여기서 나온다

한 가지 관측: 앱을 재설치한 직후에도 `BOOT_COMPLETED` 가 한 번 도착했다(에이전트가 살아
있는 상태였으므로 아무 일도 하지 않았다). 표준 동작은 아니고 삼성 쪽 특성으로 보인다.
무해하지만, 이 브로드캐스트가 실제 부팅만을 뜻한다고 가정하지 말 것.

## 검증된 성질 (Galaxy Tab S9+ / One UI 8, 2026-08-30)

- `PPID = 1` — init 으로 재부모화됐다. adbd 를 죽이거나 무선 디버깅을 꺼도 영향받지 않는다
- 30초 주기로 `agent.beat` 갱신 (충전기 없으면 120초)
- 잔량 판단 정확: 68% / low=70 → `want=0`
- 앱 크래시 0
- 앱 재설치 후 앱을 열면 ping 에 답하지 못하는 옛 에이전트가 자동으로 교체됨
- 설정 변경이 버튼 없이 전파됨: 슬라이더 조작 → `agent.conf` 즉시 갱신 → 한 주기 내 반영
- 밴드 전이 실측: `keep`(밴드 안쪽) → `want=1` 이 10초 내, 전류 479mA → 0 근처(평균 -51mA)
