# 3차 실험 설계 — 착탈 타이밍까지 스크립트가 강제한다

2차에서 배운 것:
- `Charge counter`는 0.1%(10090 µAh) 해상도 → **구간을 길게, 누적으로** 봐야 한다
- 착탈 대조군이 유효했다 → **계속 쓰되, 타이밍을 사람이 기억하지 말고 스크립트가 강제한다**
- 부하가 상수여야 비교가 성립한다 → **화면 유지·자동밝기 끔·밝기 고정**을 스크립트가 처리

## 판정해야 할 것 (우선순위 순)

1. **꽂고 `pt=1`일 때 배터리가 방전되는가, 평평한가** ← 진짜 바이패스 vs 단순 충전중단
2. **게임 없이 ADB로만 켜도 같은 거동이 나오는가** ← 프로젝트 성립 여부
3. 무엇이 `pass_through`를 0으로 되돌리는가 ← 재적용 주기

---

## A. 폴링 테스트 (2분, 충전기 무관) — 먼저

```sh
# 게임을 켠 상태에서
adb shell settings get system pass_through            # 1
adb shell settings put system pass_through 0
for i in $(seq 12); do
  printf '%2ds  %s\n' $((i*5)) "$(adb shell settings get system pass_through | tr -d '\r')"
  sleep 5
done
```

| 결과 | 의미 |
|---|---|
| 몇 초 내 1로 복귀 | 게임 부스터가 주기적으로 재적용. 게임 안 켠 상태에선 경합자가 없으니 우리 값은 유지될 것 |
| 계속 0 | 상태 변화 시점에만 쓴다(edge-triggered). **우리에게 이상적** |

이어서 **게임을 종료**하고 값을 확인 → 게임 부스터가 0으로 되돌리는지.
그 다음 **화면을 껐다 켜고**, **재부팅 후**에도 확인. 되돌리는 주체를 특정한다.

## B. 본 실험 — `tools/experiment.sh`

스크립트가 구간마다 *"충전기를 뽑고 Enter"* / *"꽂고 Enter"* 를 지시하고,
실제 `plug` 상태를 확인한 뒤 **30초 안정화**(PD 재협상·상태보고 지연을 버림)하고 나서 샘플링한다.
구간 중에 `plug`이나 `pass_through`가 바뀌면 그 구간에 ⚠를 붙여 **버리라고 표시**한다.

### 준비
- 배터리 **55~70%** (80% 넘으면 원래도 충전이 느려져 구분 안 됨)
- PPS 충전기, 케이블 고정 (실험 중 흔들리면 안 됨)
- 태블릿 화면이 보이는 곳에 두기 (스크립트가 화면을 30분 유지로 바꾼다, 종료 시 원복)
- 충전기 착탈은 **스크립트가 시킬 때만**

### E2 — 게임 없이 ADB 단독 (본 실험, 약 30분)

```sh
./tools/experiment.sh e2-adb
```

| 구간 | plug | pt | 목적 |
|---|---|---|---|
| U1 | 뽑음 | 0 | **시스템 부하 기준선** — 이 방전 속도가 잣대다 |
| C1 | 꽂음 | 0 | 정상 충전 속도 |
| B1 | 꽂음 | **1** | ★ ADB 단독 트리거 |
| U2 | 뽑음 | 1 | pt=1이 방전 자체엔 영향 없는지 (대조) |
| B2 | 꽂음 | **1** | ★ 재현 |
| C2 | 꽂음 | 0 | 충전 복귀 + 잔량 드리프트 보정 |

각 구간 5분(기본). 짧게 하려면 `DUR=180 ./tools/experiment.sh e2-adb`.

### 판정표

| B1·B2 평균 전류 | 해석 |
|---|---|
| **≈ 0** | **진짜 바이패스. 완전 성공** → 04번 앱 계획 착수 |
| U1과 비슷한 음수 | 충전만 멈춘 것. **배터리가 시스템을 먹인다 → 수명에 오히려 나쁨.** 프로젝트 재검토 |
| C1의 1/3 이하 양수 | 부분 성공. 목적상 충분 (README「목적과 인정된 한계」) |
| C1과 비슷 | ADB 단독으로는 안 됨 → C로 |

C1 ≈ C2 여야 잔량 드리프트가 결과를 오염시키지 않았다는 뜻이다. 많이 다르면 구간을 짧게 해서 재측정.

### E1 — 게임 켠 채로 (정답지, 약 25분)

E2 결과를 비교할 기준이 필요하면:

```sh
./tools/experiment.sh e1-game
```

공식 기능이 켜졌을 때의 "정상 바이패스 서명"을 확보한다.
**E2의 B1/B2가 E1의 gB1/gB2와 닮았으면 ADB 트리거가 동등하다는 뜻이다.**

E2가 애매하게 나왔을 때만 돌리면 된다. 명확하면 생략 가능.

## C. B가 실패했을 경우 — 포그라운드 조건

`pass_through`만으로 부족하고 "게임이 앞에 있다"를 따로 검사한다는 뜻.

```sh
adb shell pm list packages | grep -i honeyplayplus
```

없으면 굿락에서 **Game Booster+** 모듈 설치 → "게임 카테고리 설정"에서 개발용 앱 하나를
게임으로 재분류 → 그 앱을 포그라운드에 두고 B1 재측정.
재분류만으로 되는지, 재분류 + `pass_through` 수동 세팅이 필요한지 구분한다.

## D. 참고 — 진짜 전류값

`dumpsys battery` 전체를 한 번 떠서 전류 필드가 있는지 확인:
```sh
adb shell dumpsys battery
```
없으면 셸에서는 방법이 없다(sysfs 차단). 그때는 **Ampere/AccuBattery** 앱으로 화면에서 읽거나,
04번 앱에서 `BatteryManager.BATTERY_PROPERTY_CURRENT_NOW`로 읽는다 —
**앱에서는 권한 없이 읽힌다.** 셸에서 막힌 값을 앱은 볼 수 있다.
