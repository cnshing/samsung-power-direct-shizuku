# 최종 측정 결과 — ADB 단독 바이패스 검증 완료

측정일: 2026-08-30 00:00~00:22 (KST)
기기: Galaxy Tab S9+ (SM-X810, `gts9pwifi`) / Android 16 / One UI 8
배터리: 37~39%, ASOC 100%, 최초 사용일 2024-05-29
충전기: AC, `charge_type:1`, `charger_type:3`, `hvc:true` (고전압 충전 협상됨)
측정: `adb shell dumpsys battery` 의 **`current now` (mA)** 직접 판독

## 결론

**게임을 실행하지 않고 ADB로 `settings put system pass_through 1` 만 써도
진짜 배터리 바이패스가 걸린다. 8코어 포화 부하에서도 유지된다.**

## 측정표

| 구간 | 부하 | 충전기 | `pass_through` | 배터리 전류 | 비고 |
|---|---|---|---|---|---|
| U0 | 유휴 (런처) | ✗ | 0 | **−792 mA** | 시스템 소모 기준선 |
| C1 | 유휴 | ✓ | 0 | **+4600 mA** | 정상 충전 |
| **B1** | 유휴 | ✓ | **1** | **−16 mA** | ★ ADB 단독, 게임 없음 |
| C2 | 유휴 | ✓ | 0 | +4650 mA | 가역성 (뒷부분 충전기 빠져 폐기, 앞부분 유효) |
| L1 | 8코어 포화 | ✗ | 0 | **−1527 mA** | 고부하 소모 기준선 |
| L2 | 8코어 포화 | ✓ | 0 | **+3846 mA** | 고부하 중 충전 |
| **L3** | 8코어 포화 | ✓ | **1** | **+98 mA** | ★ 카운터 적분 95초간 **정확히 0 µAh** |

부하는 Termux + Node.js 8워커 busy loop (`top`: `800%cpu 785%user 4%idle`).
화면 밝기 255 고정, 화면 유지 30분.

## 왜 이것이 "진짜 바이패스"의 증명인가

L3에서 시스템은 **1527 mA를 소비**하는데 배터리 전류는 **0**이다.
그 1527 mA는 충전기가 직접 공급한 것 외에 나올 곳이 없다.

세 가설의 예측값과 대조하면 판정이 명확하다:

| 가설 | L3 예측값 | 실측 |
|---|---|---|
| 진짜 바이패스 (배터리 우회) | ≈ 0 | **+98 mA ✓** |
| 충전만 중단 (배터리가 시스템 공급) | ≈ −1527 mA | ✗ |
| `pass_through` 무시됨 | ≈ +3846 mA | ✗ |

카운터 적분이 95초 동안 정확히 0 µAh인 것이 가장 강한 증거다.
전류 샘플의 ±100 mA 진동은 미세 조정이고 순 이동이 없다.

## 부수 확인

- **XDA의 "30~70mA 잔류" 반론보다 낫다.** 이 기기 유휴 조건에서 −16 mA.
- **온도**: 고부하 충전(L2) 32.0→32.2℃ 상승 vs 고부하 바이패스(L3) 31.8℃ 안정.
  유휴에서도 충전 31.8~32.0℃ vs 바이패스 31.1~31.7℃.
- **전환 과도구간이 있다.** pt를 1로 쓴 뒤 첫 10~20초는 값이 튄다(−1631, −466 → 수렴).
  **앱에서 효과를 판정하려면 20초는 기다려야 한다.**
- **가역성**: pt=0으로 되돌리면 즉시 +4600 mA 충전 복귀.
- `batteryCurrentEvent`는 `0x40000000` 으로 고정, pass_through 전환에 반응하지 않았다.
  (충전기 착탈 시에는 `0x40020000`/`0x40020004` 로 변함 — 이벤트 로그에서 관측)
  → 커널 current_event 마스크는 이 기능의 지표가 아니다.

## 새로 발견한 측정 수단 — `dumpsys battery`

03번에서 "sysfs가 막혀 전류를 볼 수 없다"고 했으나, **삼성 `dumpsys battery`가 전류를 그대로 준다**:

```
  current now: -723          ← mA, 음수 = 방전
  Charge counter: 3783750    ← µAh, 10090 단위로 양자화 (용량의 0.1%)
  batteryCurrentEvent: 1073741824
```

이벤트 로그(`[BattActionChangedLogBuffer]`)에는 `current_avg`, `charge_type`, `charger_type`,
`hvc`, `current_event`, `cc` 가 2~3분 간격으로 남는다. 과거 이력 추적에 쓸 수 있다.

`current now` 단위가 mA임은 카운터 증분과의 교차검증으로 확인했다
(예: cc 5660490→5549500 / 150초 = −2.66 A vs 보고된 `current_avg:-2771`).

## 앱 대상 앱 인식 여부 (부수 확인)

| 앱 | 게임런처 인식 | 근거 |
|---|---|---|
| `com.roblox.client` | **게임** | 게임런처 목록에 표시됨 (사용자 확인) |
| `com.pjsekai.kr` | **게임** | 포그라운드 시 pass_through→1 |
| `com.termux` | **게임 아님** | 포그라운드인데 pass_through 0 유지 (C2, L1~L3) |
| `com.sec.android.app.launcher` | 게임 아님 | 동일 |

**포그라운드에 게임 아닌 앱을 두고도 바이패스가 걸린다** — 이것이 Game Booster+ 재분류
경로가 불필요함을 뜻한다. `pass_through` 하나가 유일한 입력이다.

## 재부팅 — **값이 초기화된다** (2026-08-30 확인)

```
$ adb shell settings put system pass_through 1
$ adb shell settings get system pass_through
1
$ adb reboot
   (재접속)
$ adb shell settings get system pass_through
0
```

`Settings.System` 은 원래 영속이므로, **부팅 과정에서 누군가 0으로 되돌린다**
(배터리 서비스나 게임 부스터의 초기화로 추정). 값이 안 남는 게 아니라 덮이는 것이다.

### 함의

1. **`BOOT_COMPLETED` 리시버가 필수다.** 재부팅하면 바이패스가 풀린다.
2. **안전성이 크게 올라간다.** 10번 문서의 "앱을 지워도 1로 남아 충전이 안 되는" 위험이
   **재부팅 한 번으로 자가 치유**된다. 복구 안내가 "adb 명령"에서 **"재부팅하세요"** 로 바뀐다.
3. **무선 디버깅 포트가 재부팅마다 바뀐다** (실측: 42027 → 42451).
   자체 ADB 경로로 간다면 mDNS 탐색이 필수 — `lan-mouse-android` 의 `AdbMdns.kt` 가 이미 한다.

## 저잔량에서의 거동 (2026-08-30)

**배터리 7% 에서도 게임 실행 시 `pass_through` 가 0 → 1 로 올라간다.**

→ **설정 레이어에는 배터리 잔량 게이트가 없다.** `com.samsung.android.game.gametools` 는
오직 포그라운드에 무엇이 있는지만 보고 쓴다. 삼성 공식 문서의 "20% 이상" 요구조건은
설정이 아니라 **효과 레이어**(`BatteryService` → sysfs → 충전 IC)에 걸려 있거나,
혹은 어디에도 없고 문서만 그렇게 쓴 것이다.

이 구분이 앱 설계에 직결된다:

| 저잔량 + `pt=1` + 충전기 + **화면 켜짐** | 의미 | 앱 설계 |
|---|---|---|
| 충전됨 (+mA) | 펌웨어에 바닥이 있다 | 앱의 안전 바닥은 보조 장치 |
| 충전 안 됨 (≈0) | **바닥이 없다** | 안전 바닥이 **필수 안전장치** |

### 1차 시도는 오염되어 폐기 (2026-08-30 08:14)

10~11%에서 `pt=1` 인데 +5293 mA 로 충전됐고 도중에 `pt` 가 스스로 0이 됐다.
**그러나 이 구간은 화면이 꺼진 상태였다.** 화면 꺼짐만으로도 바이패스는 해제되므로
저잔량 바닥의 증거가 되지 못한다. `pt` 가 0이 된 것도 화면을 다시 켤 때
`gametools` 가 포그라운드를 재평가한 결과로 보인다.

**교훈: 이후 모든 측정은 `mWakefulness` 를 함께 기록한다** (`tools/floor-scan.sh` 에 반영).

### 확정된 잔량별 거동

| 잔량 | `pass_through=1` 의 효과 |
|---|---|
| 7~19% | **무시된다.** 설정값은 1로 남지만 정상 속도로 충전 (+4700 mA) |
| **20% 이상** | **완전 바이패스.** 카운터 완전 고정 |

**설정 레이어에는 잔량 게이트가 없고, 효과 레이어에만 있다.**
저잔량에서 앱이 1을 써도 시스템과 경합하지 않는다 — 값은 그대로 남고 효과만 안 걸린다.
**안전 설계상 최선이다.** 앱의 안전 바닥은 보조 장치이지 필수가 아니다.

### 수렴 시간이 잔량에 따라 다르다

| 잔량 | 완전 수렴까지 |
|---|---|
| 37~39% | **10~20초** (B1, L3) |
| 20% (문턱 직상) | **약 4~5분** |

문턱 근처에서는 급격히 떨어진 뒤(4729 → 672) 긴 꼬리를 그리며 0으로 간다.
**앱에서 효과를 판정할 때 짧은 창으로 보면 안 된다.**
