기기: Galaxy Tab S9+ / Android 16 (One UI 8) · 게임: `com.pjsekai.kr` · 2026-08-29

## 1차: 게임 부스터 토글이 무엇을 바꾸는가 — **확정**

| 단계 | 상태 | `settings system pass_through` |
|---|---|---|
| A | 충전기 없음 / 게임 없음 | `0` |
| B | PPS 충전기 / 게임 없음 | `0` |
| C | PPS 충전기 / 게임 실행 / 토글 OFF | `0` |
| D | PPS 충전기 / 게임 실행 / **토글 ON** | **`1`** |

C→D diff에서 **실제로 변한 설정값은 `pass_through` 하나뿐.** 나머지 차이는
`wallpaper_finish_drawing` 타임스탬프, `topResumedActivity`(게임 내부 액티비티 전환),
그리고 C·D 양쪽에 동일하게 찍힌 프로바이더 권한 에러였다.

→ **03번 문서의 XDA 단일 출처 주장이 이 기기에서 직접 확인됐다.**
   `Settings.System.pass_through` = 게임 부스터 우회충전 토글.

부수 확인:
- 게임 실행(B→C)만으로는 `pass_through`가 안 바뀐다. **토글이 진짜 스위치다.**
- `Settings.System` 네임스페이스다 (`secure`/`global` 아님).

## 2. 막힌 것: sysfs 읽기

```
$ adb shell cat /sys/class/power_supply/battery/current_now
cat: /sys/class/power_supply/battery/current_now: Permission denied
```

**예상과 다름.** AOSP `shell.te`는 shell 도메인에 `sysfs_batteryinfo:file r_file_perms`(읽기)를
주는데, One UI 8에서는 읽기까지 막혀 있다. 삼성이 sepolicy를 더 조인 것.
→ 03번 문서의 "읽기는 가능" 항목은 **이 기기에서 반증됨.**

쓰기가 막힌 건 어차피 예상대로이므로 결론(비루팅 sysfs 직접 제어 불가)은 그대로다.

### 대체 측정 수단
1. **`dumpsys battery`의 `Charge counter`(µAh)** — 앱/셸에서 권한 없이 읽힌다.
   충전기 꽂힌 채 이 값이 **평평하면** 배터리로 전류가 안 들어가는 것.
   → `tools/watch-battery.sh`
2. **`BatteryManager.BATTERY_PROPERTY_CURRENT_NOW`** — 앱에서 **권한 없이** 읽을 수 있다.
   04번의 앱을 만들면 이걸로 정확한 전류를 볼 수 있다. 셸에서 막힌 값을 앱은 볼 수 있는 구조.

## 3. 게임런처 프로바이더 — 셸에서 접근 불가

```
SecurityException: Permission Denial: opening provider
  com.samsung.android.game.gamehome.provider.GameLauncherProvider
  from (null) (pid=..., uid=2000)
  requires com.samsung.android.game.gamehome.permission.READ_CONTENT
        or ...WRITE_CONTENT
```

uid=2000 = shell. 게임 목록 조회/삽입 경로는 **ADB로 막혀 있다.**
03번에서 "insert가 되면 Game Booster+ 없이 임의 앱을 게임으로 등록 가능"이라 했던 가능성은 닫혔다.

**다만 이제 이 경로가 필요 없다.** `pass_through`를 직접 쓸 수 있다면 게임 목록에 등록할 이유가 없다.

# 2차 측정 (21:20~21:26) — 시사적이지만 오염됨

## 먼저: `Charge counter`는 전류계가 아니다

관측된 증분이 전부 `10090 µAh`의 배수다 (10090 / 20180 / 30270).
**Tab S9+ 설계용량이 10090 mAh이므로, 이 카운터의 양자화 단위 = 용량의 정확히 0.1%.**

즉 `Charge counter`는 사실상 **0.1% 해상도의 배터리 잔량**이지 전류 측정이 아니다.
20초 샘플 하나로는 0.6A 미만을 구분할 수 없다.
→ **구간을 길게 잡고 누적으로 봐야 한다.** 스크립트에 누적/평균 mA 컬럼을 추가했다.

## 음수 델타는 측정 오류가 아니다

`plug=none`, `status=3`(방전) 구간이다. 실제로 배터리를 쓰고 있었다.

- 21:21:15 → 21:23:57: **−50450 µAh / 162초 = 평균 1.12 A 방전**
- 화면 켜짐 + 리듬게임(`com.pjsekai.kr`) 구동 중이면 타당한 소모량이다.

**이 1.12 A 라는 숫자가 다음 실험의 핵심 잣대가 된다.** 아래 참조.

**`plug`이 none ↔ ac 로 바뀐 것은 오염이 아니라 의도된 대조군이다** — 뽑고 두 샘플, 꽂고 두 샘플을
반복한 것. 덕분에 같은 부하 조건에서 착탈만 바꾼 비교가 가능해졌다.

### 그래서 결정적인 게 하나 보인다

| 시각 | pt | plug | status | Δ |
|---|---|---|---|---|
| 21:21:56 | 1 | **ac** | **4 = NOT_CHARGING** | −10090 |
| 21:22:16 | 1 | **ac** | **4** | −10090 |
| 21:22:36 | 1 | **ac** | **4** | 0 |

`BATTERY_STATUS_NOT_CHARGING` = **"전원은 연결됐는데 충전하지 않는다".**
우회충전이 프레임워크에 보고되는 모습 그 자체다. 게임 부스터가 실제로 충전을 끊었다는 직접 증거.

두 번째 착탈(21:24:17~)에서는 `status=2`(충전)로 보고되면서도 카운터는 61초간 불변이었다.
상태 보고가 실제 거동보다 늦거나, 바이패스 진입에 시간이 걸리는 것으로 보인다.

## 그래도 건진 것: 깨끗한 창 하나

| 시각 | pt | plug | status | counter | Δ |
|---|---|---|---|---|---|
| 21:24:17 | **1** | ac | 2(충전) | 8152720 | 0 |
| 21:24:38 | **1** | ac | 2 | 8152720 | 0 |
| 21:24:58 | **1** | ac | 2 | 8152720 | 0 |
| 21:25:18 | **0** | ac | 2 | 8152720 | 0 |
| 21:25:38 | 0 | ac | 2 | 8172900 | **+20180** |
| 21:25:59 | 0 | ac | 2 | 8193080 | +20180 |
| 21:26:19 | 0 | ac | 2 | 8213260 | +20180 |
| 21:26:39 | 0 | ac | 2 | 8243530 | **+30270** |

`plug`도 `status`도 앞뒤가 동일하다. **바뀐 변수는 `pass_through` 하나뿐이다.**

- `pt=1` 구간: 61초 이상 카운터 불변 → **충전 전류 상한 0.6 A**
- `pt=0` 직후: 20180 µAh/20s = **3.63 A**, 마지막 샘플 30270/20s = **5.45 A**
- **온도**: pt=1 동안 32.2~32.4℃ → pt=0 후 32.6 / 32.9 / 33.0 / 33.1℃ 로 상승

→ **최소 6배 이상의 충전 전류 차이.** 방향성은 명확하다. 다만 표본이 61초라 정량값은 아니다.

## 새로 밝혀진 중요한 사실 (사용자 관측)

> **충전기 연결 여부와 무관하게, 게임이 켜져 있기만 하면 `pass_through`가 1로 올라간다.**

이게 구조를 알려준다. `pass_through`는 충전 협상의 결과가 아니라
**게임 상태 감시자(게임 부스터/GOS)가 세우는 "요청 플래그"** 이고,
충전 서브시스템이 그걸 읽어서 조건이 맞을 때 소비한다.

→ **우리에게 좋은 소식이다.** 플래그가 시스템으로 들어가는 *입력*이라면,
우리가 직접 써도 동등할 가능성이 높다. 관건은 "누가 그 값을 되돌리느냐"뿐이다.

## 다음 실험이 판정해야 할 진짜 질문

"충전이 멈추는가"가 아니라 **"멈춘 동안 시스템은 무엇을 먹는가"** 다.

| 꽂고 pt=1 일 때 카운터 | 해석 | 배터리 수명에 |
|---|---|---|
| **≈ 0 (평평)** | 진짜 바이패스. 시스템이 충전기에서 직접 먹는다 | **좋다** |
| **≈ −1.12 A** (뽑았을 때와 동일) | 충전만 멈춘 것. **배터리가 시스템을 먹이고 있다** | **나쁘다** — 오히려 사이클을 돈다 |
| ≈ +3.6 A | 아무 효과 없음 | — |

기존 데이터는 첫 번째를 시사한다(꽂고 pt=1 구간에서 61초 이상 평평 vs 뽑았을 때 −1.12A).
하지만 표본이 짧아 확정이 아니다. **이게 3차 실험의 1순위 목표다.**

## 해소됨 — 이 런의 `pt=1`은 게임이 세운 값이다

사용자 확인: 21:25:18에 `pt`가 0으로 떨어진 것은 **게임을 종료했기 때문**이다.
즉 이 런의 `pt=1`은 전부 게임 부스터가 세운 값이고, **ADB 단독 트리거는 아직 검증되지 않았다.**

이 런이 증명한 것 / 못 한 것:

| | |
|---|---|
| ✅ 증명됨 | 공식 기능이 실제로 충전을 끊는다 (`status=NOT_CHARGING`, 전류 6배 차이, 온도 상승 억제) |
| ✅ 증명됨 | `pass_through`가 그 기능의 상태를 정확히 반영한다 |
| ❌ 미검증 | **게임 없이 ADB로 쓴 `pass_through=1`이 같은 효과를 내는가** ← 08번 E2 |

## 되돌리는 주체 (일부 확정)

| 사건 | `pass_through` | 근거 |
|---|---|---|
| 게임 실행 | 0 → 1 | 1차·2차 측정 |
| **게임 종료** | **1 → 0 (20초 이내)** | **2차 측정 21:24:58→21:25:18** |
| 충전기 착탈 | 변화 없음 (1 유지) | 2차 측정, 착탈 4회 동안 pt=1 유지 |
| 화면 끔 / 재부팅 / 방치 | 미확인 | 08번 A절 |

→ **게임 부스터는 게임 실행/종료 시점에 이 값을 쓴다.** 충전기 상태와는 무관하게 움직인다.
   앱 설계 관점에선 "게임을 켰다 끄면 우리 값이 지워진다"는 뜻이므로, 재적용이 필요한 근거가 된다.

# A. 폴링 테스트 결과 — **트리거 모델 확정**

게임 실행 중 ADB로 `pass_through=0`을 써넣고 5초 간격으로 관찰. 3회.

| 런 | 조작 | 결과 |
|---|---|---|
| 1 | 게임 포그라운드 유지, 아무것도 안 건드림 | **60초 내내 0 유지** |
| 2 | 도중에 **화면 끔** | 15초까지 0 → **20초에 1로 복귀** |
| 3 | 도중에 **충전기 뽑고 꽂음** | **30초 내내 0 유지** |

추가 확인 (사용자):
> 액티비티를 끄는 것과 무관하다. **밖으로 나가지면 그게 트리거**다.
> 앱을 죽이지 않고 나중에 다시 들어가면 다시 1로 올라간다.

## 확정된 모델

```
com.samsung.android.game.gametools 는 포그라운드 전이 시점에만 pass_through 를 쓴다.

    전이 발생 시 포그라운드가 인식된 게임   →  pass_through := 1
    전이 발생 시 포그라운드가 게임이 아님   →  pass_through := 0
        (앱 전환, 화면 끔/켬 모두 전이로 친다)
```

**이 모델은 트리거 매트릭스 실험으로 최종 확정됐다 ([12](12-trigger-matrix.md)).**
중간에 "모든 전이가 값을 지운다"고 의심한 적이 있으나 **오측이었다** — 화면이 꺼져 있던
오염된 관측이었고, 그때도 직전에 게임이 포그라운드였던 것으로 설명된다.

- **폴링하지 않는다.** 주기적 재적용이 없다 (런 1: 60초간 우리 값이 그대로 유지됨)
- **충전기 상태를 보지 않는다** (런 3, 그리고 2차 측정에서 착탈 4회 동안 pt=1 유지)
- **액티비티 생명주기가 아니라 포그라운드 여부**가 기준이다
- 화면 끔 = 포그라운드 상실. 화면을 다시 켜서 게임으로 돌아가면 재진입으로 1

## 프로젝트에 주는 함의 — **매우 유리하다**

1. **우리가 쓴 값을 덮을 주체가 사실상 없다.** 인식된 게임이 포그라운드를 얻거나 잃지 않는 한
   아무도 이 값을 건드리지 않는다. 게임을 안 하는 동안은 경합자가 0이다.
2. **재적용 주기를 짧게 잡을 이유가 없다.** 20~30분은 오히려 여유롭다.
   게임 세션이 끝난 뒤 한 번만 복구하면 되는 수준.
3. **구조적으로 `pass_through`가 이 기능의 유일한 입력일 가능성이 높다.**
   게임 부스터가 포그라운드 전이만 보고 이 값 하나만 쓴다면, 충전 서브시스템 쪽에서
   "게임이 앞에 있나"를 따로 볼 이유가 없다. → E2 성공 가능성을 높게 본다.

- 장시간(수 시간) 방치
